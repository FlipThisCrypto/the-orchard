## 1. Decisions made (treat these as settled)

### D0. NORTH STAR — serverless Orchard (ADR-0008). Read this first.
The end state is a system with **no servers and no upkeep**: each Tree is an
on-chain singleton proving uptime via timelocked heartbeat spends
(`secp256r1_verify` + `ASSERT_SECONDS_RELATIVE` + state counter), rewards are
claimed from on-chain epoch vaults gated by Pass-NFT ownership, epoch
rollover is a permissionless crank, and all clients are static pages reading
chain state. Full design, accepted residue (broadcast endpoints, raw-data
hosting, physical truth, fees), and migration plan are in
`docs/decisions/0008-serverless-target-architecture.md`.

**Operating rule for every task below:** the central oracle (D1) is now a
TRANSITIONAL BRIDGE. Before investing effort in any oracle feature, ask "does
this transfer to the serverless architecture?" If no, build the minimum that
unblocks testers. Puzzles ship in ChiaLisp (Rue is bleeding-edge; prototype
only).

### D1. Central oracle for v1 — NOT per-operator, NOT on-device — and now explicitly TEMPORARY
The idea of running the oracle / DataLayer posting / a DataLayer mirror on the
ESP32 itself is **rejected as infeasible**. DataLayer requires a Chia full node
+ DataLayer service (GBs of state, a funded wallet, on-chain spends per root
update). A mirror is not lighter — it serves files generated by the DataLayer
service and needs a wallet spend to register.

New v1 topology:

```
Tree (ESP32) --signed reading, HTTPS--> Central Oracle (VPS, run by project)
                                            |  per-Season batch
                                            v
                                   Chia DataLayer (ONE store,
                                   ONE root update per Season)
```

- Trees stay "dumb but honest": sign every reading, POST it, nothing else.
- Operators need **zero extra hardware** — this satisfies the original goal
  better than on-device DataLayer would have.
- ONE DataLayer store for the whole network. Per-Tree attestation rows live as
  keys inside it. One batched root update per Season (~daily), not hundreds of
  on-chain transactions.
- Decentralization path stays the planned Keeper layer (v2): Keepers can
  independently verify the dataset because readings are device-signed
  (ed25519, see D2). Trust story: "you don't trust the oracle; you verify
  signatures + the on-chain Merkle root."

### D2. Device signing curve: secp256r1 — AMENDED, supersedes ed25519 (ADR-0007)
PR #1's verifiable-dataset direction stands, but the curve changes: **CLVM has
no ed25519 operator** — its signature ops are BLS, secp256k1, and secp256r1.
The North Star (D0) requires puzzles to verify Tree signatures on-chain, so
device keys are **secp256r1 (P-256), ECDSA/sha256, RFC 6979 deterministic**,
via mbedTLS on the ESP32. Full rationale + implementation checklist:
`docs/decisions/0007-secp256r1-device-keys.md`. **Apply to PR #1 BEFORE
merging** — re-keying a deployed fleet later is far more expensive. Bonus:
P-256 matches ATECC608-class secure elements for a future hardware-key Tree
revision. All other PR #1 guidance stands: get it reviewed, rebased,
CI-green, merged early.

### D3. Replay protection: monotonic `seq` counter
Already specified in detail — see `replay-protection.md` (delivered separately;
incorporate it into the repo, e.g. `docs/decisions/` or as implementation).
Summary: NVS-persisted strictly-increasing counter on the Tree (reservation
blocks of 256 to limit flash wear), included in the signed payload; oracle
stores `last_seq` per Node, rejects `seq <= last_seq` with 409, resets to 0 on
re-registration. **The counter goes inside the ed25519-signed payload** once
PR #1 merges — the scheme is signature-agnostic.

### D4. Internet-facing oracle ⇒ TLS, rate limiting, Postgres path
Because the oracle is now central and public:
- TLS is mandatory. Use a reverse proxy (Caddy — automatic Let's Encrypt).
- Add basic rate limiting (per-node and per-IP) at the proxy or app layer.
- SQLite + WAL mode is fine for testing; plan Postgres at a few hundred
  Trees. Fleet expectation: **100–1,000 Trees within 6 months.**
- Add Alembic now (the codebase docstring already promises it) so the
  `last_seq` column and future schema changes are real migrations.

### D5. OTA must be signature-verified before launch
Trees are currently physically reflashed; OTA is required pre-launch. Unsigned
OTA on internet-connected devices = fleet-wide compromise if the update URL is
ever hijacked. Use ESP-IDF native signed app images (RSA/ecdsa via
`CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT` as the minimum: verify-on-update
without full secure boot). The release workflow (Task T2) is where builds get
signed. The signing private key lives in a GitHub Actions secret; the public
key is compiled into firmware.

### D6. NTP time on the Tree
Add SNTP (`configTime()`) after WiFi connect. Gives real UTC on readings
without GPS fix — better data quality and enables a timestamp freshness check
to complement `seq`. GPS time remains preferred when a fix exists.

### D7. Release cadence
Tag `vX.Y.Z` whenever `firmware/include/version.h` bumps. The release workflow
does the rest. Repo is public ⇒ GitHub Actions is free/unlimited — run the
full CI matrix, no trimming.

### D8. Community scaffolding: minimal for now
A few testers, not open recruitment yet. Add only: `SECURITY.md` (disclosure
contact) and one bug-report issue template. Skip CoC/Discussions/etc. for now.

### Explicitly deferred (do NOT work on these)
- GPS/location spoofing defenses → post-PoC (Keeper layer).
- Sensor-data plausibility gating of rewards → v2. v1 rewards = uptime + stats.
- Operator self-service payouts → later. Owner runs the harvest script manually.

- Write the replay check so it's multi-worker-safe under Postgres: guarded

### T6. NTP support in firmware (D6)

## 2b. Phase 2 task list (T9–T17)

Execute after T1–T8, except where noted. **T9–T11 block shipping hardware to
testers** — prioritize them as soon as CI + replay protection are merged.

### T9. Remote provisioning / claim-code onboarding (BLOCKS TESTERS)
Current onboarding assumes the operator runs the oracle locally (USB-serial →
local dashboard → register). With the central oracle, a remote operator must
be able to: flash via web flasher → bind THEIR wallet to THEIR device on OUR
oracle. Design and implement a claim-code flow:
- First boot, unprovisioned: Tree generates identity, derives a short
  human-readable claim code (e.g. 8 chars from a hash of pubkey + nonce),
  shows it over serial AND on its WiFi-setup captive portal page.
- Hosted claim page (can live on the oracle): operator authenticates with
  wallet session, enters claim code; oracle binds node_id ↔ DID/Pass.
- Tree polls a `/provision/<claim>` endpoint until claimed, then begins
  normal posting. Claim codes expire (e.g. 24h) and are single-use.
- Write this up as ADR-0005 before implementing; it defines first-boot
  firmware behavior and is expensive to change after devices ship.

### T10. Device secret protection — flash + NVS encryption (BLOCKS TESTERS)
The signing secret currently sits in NVS in plaintext; USB access = permanent
device impersonation. Enable ESP32 flash encryption + NVS encryption
(eFuse-based; supported on WROOM and S3 targets). Cautions:
- eFuse burns are IRREVERSIBLE per device — document the procedure in
  `docs/` and test on sacrificial boards first.
- Changes the flashing procedure (encrypted images / `--encrypt` flag);
  update the web-flasher docs and release workflow accordingly.
- Use "release" mode only when procedure is proven; "development" mode for
  bench boards.

### T11. Tree simulator (BLOCKS TESTERS; also a CI asset)
`tools/tree_sim/` — Python script emulating N virtual Trees:
- Generates identities, registers (or uses pre-seeded test nodes), posts
  correctly signed readings (HMAC now, ed25519 after PR #1) at a configurable
  interval, with realistic sensor value drift and proper `seq` handling.
- Modes: functional (1 tree, verbose) and load (N=1000, report latency/error
  rates against a target oracle).
- Add a CI job running a short end-to-end sim against an ephemeral oracle
  instance — this becomes the integration test the repo currently lacks.

### T12. Hosted operator status page
Minimal read-only web page served by the oracle (or static page hitting its
read endpoints): per-Tree last-seen, hours credited this Season, Pass
binding, fw version. Stretch: public network map of live Trees (lat/lon
already collected) — the 10-second demo of the whole project. No wallet
required to view; wallet session required only to see one's own detail view.

### T13. Offline alerting
Cron/systemd timer on the oracle: flag Trees silent > 2h; log + (later) email
the operator. Protects the network's core value (uptime) — today a dead Tree
is only discovered at payout. Start with a simple table + log line; email can
come after PoC.

### T14. Data-quality ADR + payload schema versioning
- ADR-0006: classify sensors as trusted-grade (digital, e.g. BME280-class)
  vs indicative (uncalibrated analog, e.g. MQ-135); define burn-in procedure
  for gas sensors in operator docs; state that v1 rewards are uptime-based
  and data-quality gating is v2 (consistent with deferred list).
- Add `schema: <int>` to the reading payload NOW (cheap), so a mixed-firmware
  fleet can evolve payload formats safely. Oracle stores it per reading.

### T15. License cleanup
Repo currently carries Apache-2.0 AND `docs/The_Orchard_Open_Source_License_v1.pdf`.
Pick ONE (owner indicated Apache-2.0 direction — confirm with owner before
deleting anything). Remove or clearly mark the other as historical; ensure
SPDX headers match the chosen license. Ambiguous licensing deters exactly the
contributors being recruited.

### T16. DataLayer fee & ops policy
Each Season root update is an on-chain spend. Define in ADR or
`orchard_chia/` docs: fee amount policy, confirmation monitoring (alert if a
root update hasn't confirmed within N blocks), and the failure mode: if
Season N's publish fails, Season N+1's update must carry/include it (the
attestation data must never be silently dropped). Implement the confirmation
check in the Season writer.

### T17. $JUICE treasury transparency
Update `JUICE.md` (or equivalent) with: total supply, allocation table
(rewards pool / team / liquidity / reserve), the payout wallet address, and
emission expectations per Season. Note in the doc that token/reward mechanics
should get qualified legal review before broad public launch — do not present
the doc as legal or financial guidance.

## 3. Constraints & context the session must respect

- **OS-agnostic:** owner develops on Windows; contributors may be on
  Linux/Mac. Keep docs dual-path (the README already does
  `\.venv\Scripts\activate` vs `source`). Don't break the serial/COM-port
  dashboard flows.
- **Don't break the local-oracle dev path.** Central oracle is the production
  story; the local FastAPI + Flask dashboard remains the dev/test loop.
- **Existing conventions to follow:** SPDX headers on every file, ADRs in
  `docs/decisions/`, lessons in `docs/LOG.md`, brand-name↔code-name glossary
  (Tree=node, Season=reward cycle, etc.), settings-flag staged rollouts
  (precedent: `require_wallet_session`).
- **No secrets in the repo** — wallet config stays in gitignored
  `orchard_chia/config.yaml`; OTA signing key only in Actions secrets.
- **Hash-pinned lockfiles are a selling point** — never let requirements and
  locks drift (CI job T1.2 enforces this).
- Payouts remain a manually-run, dry-run-by-default, watermark-idempotent
  script (`python -m orchard_chia.payout`). Don't automate sending without
  explicit owner instruction.
