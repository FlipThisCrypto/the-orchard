## Pin assignments (cheat sheet)

### WROOM-32U (`freenove_esp32_wroom` env)

| Sensor | GPIO | Notes |
|---|---|---|
| GPS RX (from GPS TX) | 18 | overridden via `-D` |
| GPS TX (to GPS RX) | 19 | overridden via `-D` |
| MQ-135 AOUT | 34 | ADC1_CH6 on classic ESP32, default in pins.h |
| I²C SDA (BME280) | 21 | default |
| I²C SCL (BME280) | 22 | default |
| DS18B20 DATA | 25 | needs 4.7 kΩ pull-up to 3V3 |
| Status LED | 2 | Freenove convention |

### ESP32-S3 (`freenove_esp32s3` / `freenove_esp32s3_uart` envs)

| Sensor | GPIO | Notes |
|---|---|---|
| GPS RX (from GPS TX) | 4 | default (from pins.h) |
| GPS TX (to GPS RX) | 5 | default |
| MQ-135 AOUT | **7** | ADC1_CH6 — overridden; GPIO 34 isn't ADC on S3 |
| I²C SDA (BME280) | 21 | default — valid on S3 |
| I²C SCL (BME280) | **9** | overridden — GPIO 22 doesn't exist on S3 module |
| DS18B20 DATA | **10** | overridden — GPIO 25 doesn't exist on S3 module |
| Status LED | 48 | Freenove S3 convention |

### Sensor wiring rules

- **MQ-135 → 5V VCC** (heater needs 5V; 3V3 doesn't work)
- **BME280 → 3V3 only** (5V kills bare BME280 breakouts without onboard regulator)
- **DS18B20 → 4.7 kΩ pull-up between DATA and 3V3** (waterproof probe kits usually include one in heat-shrink near the connector; bare TO-92 chips don't)

## Known issues (open)

### 🔴 ISSUE-1 — S3 board (COM12) power-cycles after WiFi.begin

> **UPDATE 2026-06-02 (cont.):** Root-caused and addressed in **0.4.7**.
> The trigger was DS18B20's `requestTemperatures()` blocking the main task
> ~750 ms *during* the WiFi association handshake; 0.4.7 makes the read
> non-blocking so the brownout can't recur (0.4.6's WiFi-gate was only a
> workaround). **Reflash `D8F89B9E` to 0.4.7** (`freenove_esp32s3_uart`).
> If it STILL resets ~12 s in — with no sampling involved — it's a pure
> power brownout: powered USB hub / better cable. See LOG.md.

**Symptom:** Tree boots, runs through sensor init, prints `[wifi] connecting to 'FlipThisCrypto'`, then 11.8 seconds of silence, then `rst:0x1 (POWERON)` cold reboot. Loops forever.

**Status as of session end:** Diagnosed as either DS18B20 read contention with WiFi connect (most likely), excessive `WiFi.status()` polling, or hardware brownout. Fix attempted in `f56b2d9` (0.4.6) — flash to COM12 failed because COM12 was held open by the operator's monitor. **0.4.6 not yet verified on hardware.**

**Next move:** After releasing COM12, run:
```powershell
cd "I:\DeMeter Data\Chia DePIN\firmware"
python -m platformio run -e freenove_esp32s3_uart -t upload --upload-port COM12
python -m platformio device monitor -e freenove_esp32s3_uart --port COM12
```
Press EN. Look for `[wifi] connected, ip=...` followed by `[oracle] POST -> 202`. If still reboots → it's hardware (USB cable / port / regulator); try a powered USB hub.

### 🟡 ISSUE-2 — GPS regression on WROOM Tree (COM4 / 5B9BB022…)

> **UPDATE 2026-06-02 (cont.):** Confirmed via live data + git that this is
> **HARDWARE, not firmware.** The 0.4.3 GPS code is byte-identical to the
> working 0.1.0 (only the opt-in autobaud `#if` block differs, compiled
> out), and 0.1.0 used the same `espressif32@6.7.0` floor. Latest 0.4.3
> readings show `chars_processed: 0` = zero bytes on the wire. A fix WAS
> captured on 0.1.0 (2026-05-31) but with `fix_age_ms` ≈ 33 h, i.e. the
> module had already gone silent ~05-30. **Don't rebuild the driver** —
> triage the GPS TX→GPIO18 wire / power / antenna with `GPS_RAW`. See LOG.md.

**Symptom:** WROOM-32U Tree was on fw 0.1.0, GPS reading clean coordinates. After upgrade to 0.4.x with the 0.3.0 auto-baud probe inherited, GPS shows recognizable `$GPRMC,3800.27...` fragments but every sentence fails checksum.

**Diagnosis:** The 6-cycle `end()/begin()/drain` churn in the 0.3.0 probe leaves UART1 in a degraded state on this specific hardware.

**Status as of session end:** Fixed in firmware 0.4.3 (`7552004`) by reverting to the 0.1.0 single-`begin()` path; auto-baud now opt-in via `-D ORCHARD_GPS_AUTOBAUD=1`. **WROOM has NOT been reflashed yet.** Still running 0.4.0 with the broken probe.

**Next move:** Reflash WROOM with latest firmware:
```powershell
python -m platformio run -e freenove_esp32_wroom -t upload --upload-port <wroom-com-port>
```

### 🟡 ISSUE-3 — BME280 not detected on COM12 S3

Boot log shows `[sensors] bme280 bus=0 active=no`. SCL+SDA on GPIO 9+21 with 3V3 power. Either:
- Not yet wired (most likely — operator was wiring incrementally)
- Wired but sensor isn't ACKing on the bus

**Next move:** With monitor open, type `I2C_SCAN` + Enter. If BME280 is wired:
- `OK 0x76` or `OK 0x77` → sensor visible on bus but driver init failed → driver bug to investigate

## Lessons logged (for future sessions to read)

The `docs/LOG.md` file has the running journal. Key recent entries:

### 2026-06-01 — GPS regression after 0.4.x rebuild
Don't theorize; read LOG.md + `git log -- firmware/` first. The 0.3.0 commit message described the exact symptom we were seeing again.

**The operator should not have to ask me to look up my own notes.**

### Pattern: blocking serial command handlers

If a serial command's handler blocks for more than ~250ms (WiFi.begin, DS18B20 read, anything network), it starves:
- Other serial commands (3s default timeout fires)
- WiFi internal task (can cause connect failure or chip reset)
- Sample tick (delayed)

**Rule:** every serial command must ack `OK` within ~50ms. Do blocking work asynchronously (state machine in main loop, or a flag the next loop tick picks up).

### Pattern: PowerShell env vars die with the window

`$env:NAME = "value"` lives only for the current PowerShell window. To make persistent, either set in `oracle/.env` / `dashboard/.env` (committed to gitignore) or use `[System.Environment]::SetEnvironmentVariable("NAME", "value", "User")`.

### Pattern: Multi-tab session in browser

`sessionStorage` is per-tab; `localStorage` is per-origin. For dashboards that get opened in multiple tabs, use `localStorage` + `storage` event for cross-tab sync. Did this in `connect.js`.
