# Resume point — 2026-08-11, before a Windows restart

Where to pick up after the reboot. Written because a restart of *this machine*
stops more of The Orchard than is obvious from looking at it.

---

## 1. What this machine actually is

Not a dev box. It is a production node, and it holds three roles nothing else
holds:

| Role | Port | What stops without it |
|---|---|---|
| Chia `data_layer` | 8562 | publishing and sealing to the store |
| Chia `data_layer_http` | 8575 | **anyone anywhere retrieving the store's data** |
| Chia `wallet` | 9256 | block height for anchors; any future payout |

Plus the economics ledger at `orchard_chia/data/pool_ledger.db` — a local
SQLite file, gitignored, that exists in exactly one place: here.

The oracle box (`oracle.theorchard.network`) is **not** a substitute for any of
this. It receives readings from Trees and serves the public API. It does not
write to chain and does not hold the ledger.

### The part that is easy to miss

The store has **zero mirrors**. While 8575 is down, the on-chain root still
commits to the readings, but *nobody on earth can fetch them* to check. The
tamper-evidence survives a reboot; the retrievability does not. That is the
single biggest structural gap in the project right now — bigger than the block
anchor — and it is a decision, not a bug (see §5).

## 2. What was fixed before the restart

Chia was installed as a **GUI application with no autostart entry of any
kind** — not a Run key, not a Startup shortcut. It had simply been left running
since 2026-06-30, so the dependency was invisible until a reboot was needed.
Every Orchard timer would have fired into a closed port.

Now registered (`tools/schedule_windows.ps1`, re-runnable and idempotent):

| Task | When | Notes |
|---|---|---|
| Orchard Chia Daemon | at logon + 90s | `chia start data data_layer_http` |
| Orchard Publish | hourly at :10 | readings → DataLayer |
| Orchard Attest | daily 00:25 | seal closed seasons |
| Orchard Sync | daily 00:30 | chain → oracle catch-up |
| Orchard Settle | daily 00:40 | ledger write, **not** a spend |
| Orchard Verify | daily 01:00 | independent re-derivation |
| Orchard Status | daily 08:00 | ops log |

Two things that testing caught and guessing would not have:

- `chia start data_layer` is **not valid**. The group is `data`, and the HTTP
  server is a separate group `data_layer_http`. Verified: `rc=0`, all three
  services named in the log.
- `-AtLogOn` without `-User` means "any user" and needs elevation. Scoped to
  this account it registers non-elevated.

**Tasks run only when this account is logged on.** A reboot that stops at the
lock screen runs nothing. Log in.

Paying is deliberately **not** scheduled and never will be.

## 3. Post-restart checklist

Run these in order. Expected results are given so a wrong answer is obvious.

**a. Daemons came back** (wait ~2 min after logon):

```bash
powershell -Command "foreach ($p in 8562,9256,8575,55400) { $ok=(Test-NetConnection 127.0.0.1 -Port $p -InformationLevel Quiet -WarningAction SilentlyContinue); '{0} {1}' -f $p,$(if($ok){'UP'}else{'DOWN'}) }"
```

All four `UP`. If not: `Start-ScheduledTask -TaskName "Orchard Chia Daemon"`,
then read `orchard_chia\data\ops\scheduler-orchard-chia-daemon.log`.

**b. The ledger is intact** — it is the only copy:

```bash
python -m orchard_chia.economics audit
```

Expect: `ledger is internally consistent: per-day sums, ceilings, and the pool chain all re-derive.`

**c. The chain still verifies:**

```bash
python -m orchard_chia.datalayer verify-latest
```

Expect: `VALID (anchor pending firmware)`. Anchor is the known gap. Anything
else failing is real.

**d. The Tree is reporting:**

```bash
python -m orchard_chia.economics status
```

Expect a `TREES` line reading `reporting (N min ago)`. `QUIET` or `DARK` means
the Tree, not this machine.

**e. Publishing resumed** — check after the next `:10`:

```bash
powershell -Command "Get-Content 'I:\DeMeter Data\orchard-t9fw-wt\orchard_chia\data\ops\scheduler-orchard-publish.log' -Tail 20"
```

## 5. Open decisions — yours, not mine

1. **Mirror the store.** Without one, only this machine can serve the data.
   Needs 8575 reachable from outside plus an `add_mirror` announcement, which
   spends XCH. Also: should this machine be the mirror, or a separate
   always-on host? A sole mirror that reboots is not a mirror.
2. **Deploy the oracle** (task #18) — unblocks `sync-oracle`.
3. **Block anchor** (task #9) — ride the `POST /readings` response, since the
   edge allowlists paths and `/beacon` will never be reachable. Needs firmware
   plus a reflash. This is what keeps the public badge at Unverified.
4. **Four token questions** still open in `docs/token/EMISSION.md`: terminal
   dust, Pass requirement, the public statement on the 185 legacy placeholder
   attestations, and the payout receive address.
